# VS Code 自有 Core 收尾

日期：2026-09-14。沿用已确认的 stdio 宿主/SDK graceful close 改造范围，
本步只修复扩展自己启动的 Core，不切换共享宿主、不改变模型/key 优先级，
不修改原 Console。共享宿主退出规则仍单独待确认。

## 当前问题

`CoreClient.dispose` 立即终止子进程；`AsyncResourceManager.restart` 不等待
旧资源释放，`deactivate` 同步返回。仅 kill 信号不证明 Core 已经保存并退出，
新的同目录启动还可能与旧进程释放实例锁竞争。现有 manager 单测使用同步
假资源，不能证明进程级等待。

## 本步方案与验收清单

- [x] 自有进程以 EOF 开始收尾，继续读取输出，最多等 30 秒；之后只终止
  自有子进程并最多再等 5 秒，任何超时/信号/非零退出都不得当作保存成功。
- [x] 重复关闭共享同一结果；同步 dispose 入口启动收尾并处理拒绝，扩展
  deactivate 返回可等待的关闭结果。VS Code/OS 强制退出仍不能保证等待。
- [x] manager 重启先等待旧资源，关闭失败不启动替代进程；通信意外关闭后
  也必须完成旧进程收尾再重连。启动尚未完成时关闭不泄漏资源。
- [x] 新请求在收尾开始后被拒绝，启动失败清理不能覆盖原始错误。
- [x] 先加入异步资源释放的失败回归，再实现；并发 get/restart/close、
  自然断连、延迟启动、退出失败及重入都有测试。
- [x] 真实 source Core 正常收尾及最终保存失败对照；在重开 Core 前检查
  已保存状态，不能靠启动恢复掩盖未完成的写入。
- [x] 扩展编译/完整测试、原前端零变更检查；再更新两种 VSIX 与制品边界。
- [ ] 原生 extension host 激活/退出、包内 Core 运行和跨平台验收。

实现及失败记录见 [专项验收](../testing/vscode-owned-core-shutdown-acceptance.md)。
扩展源码完整 **73/73**，两种 VSIX 实际安装后分别 **24/24** 专项通过。
资源释放失败会保留同一失败结果，不自动启动替代 Core；需先调查错误并
重新创建扩展宿主。这不把强制终止当作保存成功，也不是共享宿主策略。

本步不激活日常 VS Code 扩展、不执行打包 Core、不访问系统凭据。源码
收尾通过不能代替原生 extension host 激活/退出和跨平台安装态验收。
